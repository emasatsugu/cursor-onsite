Context: 1-day onsite interview/work trial where I'll have ~5h to implement something.

Goal: build an end-to-end feature that allows users to edit files on a cloud VM. This is a MVP/POC only — demonstrate the key components using local dev, mocking where helpful.

Requirements:
- User can create a new "thread" or continue editing on an existing thread
- User can type a prompt to the agent
- The agent is able to read_file, write_file, edit_file, as well as use shell commands
- Agent output (asst messages, tool calls, tool call results, etc) are streamed back to the user as they are generated by the model
- For now the only model we support will be OpenAI models, using an API key

Components of the system:
1. Browser / UI client
- Ability to view previous threads, view message history for a current thread, create a new thread
- WS connection to the control plane (subscribe-only for streaming; prompts go over HTTP)
- Receives streamed agent events: tool_call_start, tool_call_result, assistant_message, agent_loop_done, agent_loop_error

2. Control plane
- The only entity that has DB access
- Manages thread CRUD
- Manages VM registration, assignment, health checking, etc
- Streams agent results back to the browser
- Runs the agent loop (VM is a dumb tool executor only)
- Keeps active threads + assignments as well as all VMs in memory for now, since it needs WS conn to browser and WS conn to VM
- System prompt + tool defs are hardcoded here for POC
- Hardcoded demo userId (no auth)

"Thread creation" only happens after the user has sent the first prompt, so on thread creation via POST /threads, the control plane should:
- Look for an available VM
- If nothing available, reject
- Record entities in DB (thread, assignment) — assignment stays `active` for the life of the thread
- Send assignment to VM
- Start agent loop

"Continue thread" (follow-up prompt on an existing thread via POST /threads/:id/messages):
- Always route to the same Assignment/VM (workspace stickiness)
- Do not handle VM going unhealthy mid-assignment for now — only unassigned VMs are health-gated. Moving a thread between VMs needs git/workspace lifecycle, which is out of scope.
- Start agent loop with full prior transcript context

Agent loop
We use OpenAI Chat Completions (`chat.completions`) with tools + streaming. The model is stateless — we send the entire context on every API call: system prompt, tool defs, and all prior turn messages (loaded by concatenating every Transcript blob for the thread).
- 1. User sends prompt
- 2. Control plane constructs streaming API call to OpenAI
- 3. Stream deltas to the browser as `assistant_message` (and `tool_call_start` when a tool call begins)
- 4. Buffer tool-call deltas in memory; only dispatch to the VM once a tool call request is complete
- 5. If the model returns N tool calls in one assistant message: **parallel fan-out to the VM, await all**, then append all `role:tool` results and call the model again
- 6. If no tool calls when the model finishes the turn, emit `agent_loop_done` and exit
- 7. On failure: emit `agent_loop_error`

Tools (hardcoded defs on control plane; executed on VM):
- `read_file` — `{ path: string, start_line?: number, end_line?: number }`
- `write_file` — `{ path: string, content: string }` (create/overwrite whole file)
- `edit_file` — `{ path: string, old_string: string, new_string: string }` (unique search-replace; fail if `old_string` not found or not unique)
- `shell` — `{ command: string, cwd?: string }` → `{ stdout, stderr, exit_code }`

Durable storage during the loop (message-boundary writes):
- One Transcript row + one blob per user turn. Blob = OpenAI-style messages for that turn only (no system prompt / tool defs).
- Write on: (1) turn start → `[user]`; (2) after each model stream ends → append full `assistant` (text + complete `tool_calls`); (3) after all tool results for that step → append `role:tool` messages. Each write is a full overwrite of the blob value.
- Do **not** persist on text deltas or `tool_call_start` — those are WS-only. History reload is boundary-accurate, not live mid-stream.
- Note on blob APIs: object stores generally do **not** offer atomic append for structured JSON. Full overwrite is the right POC choice.
- Stream live events to the browser over websocket (independent of when the blob is written)

API surface:
**HTTP**
- `GET /threads` — list threads for demo user
- `GET /threads/:id` — thread metadata + ordered transcripts (resolved blob contents) for history view
- `POST /threads` — body `{ prompt }` → create thread + assignment + start loop
- `POST /threads/:id/messages` — body `{ prompt }` → follow-up on sticky VM + start loop

**Browser ↔ CP WS**
- Browser connects and sends `{ type: "subscribe", threadId }`
- CP → browser: `tool_call_start` | `tool_call_result` | `assistant_message` | `agent_loop_done` | `agent_loop_error`
- Prompts stay on HTTP; WS is subscribe-only for streaming

**CP ↔ VM WS**
- VM → CP: `register` (externalId on connect), `heartbeat`, `tool_call_response`
- CP → VM: `assignment`, `execute_tool_call`

3. VMs
The VMs will come from a shared pool — the control plane can't initiate communication with the VM; the VM comes loaded with software that initiates communication with the control plane.
For now assume the VM comes loaded with files on disk to edit — git lifecycle later if time.
The VM's "main" loop:
1. Generate a uuid as `externalId`, open a WS connection to the control plane (connection + `register` = registration)
2. Sends its unique ID
3. Listens for `assignment` and `execute_tool_call`; responds with `heartbeat` and `tool_call_response`

Local demo topology (3 processes): React FE, Node control plane, Node fake VM. CP restart mid-generation: drop in-flight, don't handle yet.

Tech stack:
- React FE
- Node control plane
- Sequelize ORM
- Node VM
- Sqlite — relational storage + simulated blob storage for MVP

Data model:
- VirtualMachine — id, externalId, status: healthy / unhealthy
- Assignment — id, vmId, threadId, status: active / completed (stays `active` for life of thread)
- Thread — id, userId (hardcoded demo user)
- Transcript — one row per user turn; 1:1 with a blob. No system prompt or tool defs. To build OpenAI context: load all Transcripts for the thread (ordered) and concatenate blob contents. Fields: id, threadId, key
- BlobStorage — key, value (messages for that turn; overwritten in full at message boundaries)
